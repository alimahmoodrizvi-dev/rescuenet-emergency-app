# RescueNet Backend — Phase 5

FastAPI + SQLAlchemy implementation of the Part 10 API surface from the Phase 1 architecture
doc, plus the WebSocket live-push channel (Part 10/23) and the AI abstraction layer (Part 8).

**This backend has been run and tested, not just written.** Every endpoint below was
exercised with live `curl` requests during development (auth → create incident → duplicate
submission → dedup confirmed → AI analysis on the exact Urdu/English example from Part 6 →
resource matching → clustering → WebSocket broadcast — all verified working), and the same
core flows are captured as an automated `pytest` suite in `tests/test_smoke.py` that passes
end-to-end (7/7).

## Quick start (local, zero setup)

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Defaults to a local SQLite file (`rescuenet.db`) — no database server needed to try it out.
Visit `http://localhost:8000/docs` for interactive Swagger docs (auto-generated by FastAPI
from the schemas in `app/schemas.py`).

Run the test suite:

```bash
pip install pytest
pytest tests/test_smoke.py -v
```

## Quick start (Docker + PostgreSQL, closer to a real deployment)

```bash
cp .env.example .env   # then edit RESCUENET_JWT_SECRET at minimum
docker compose up --build
```

This runs PostgreSQL (Part 12's recommended database) alongside the API, wired via
`RESCUENET_DATABASE_URL` in `docker-compose.yml`.

## What's implemented (Phase 5 scope)

- **Auth** (`app/auth.py`, `app/routers/auth.py`): two paths per Part 19/24 — anonymous
  device-bound JWT for citizens (`POST /api/auth/device-register`, matching the same
  `device_uuid` the Android app already generates and stores — see `UserRepository.kt`), and
  real username/password auth for Volunteer/Rescue Operator/Command Center Admin roles
  (`POST /api/auth/org-login`). Passwords are bcrypt-hashed; there's no public self-signup
  for organizational roles, deliberately — provisioning those is an ops task.
- **Incidents** (`app/routers/incidents.py`): create/list/get/update, with **real
  event_uuid-based deduplication** — verified live: submitting the same `event_uuid` twice
  returns the same row, not a duplicate.
- **Safety status / family board** (`app/routers/safety.py`): append-only status history per
  user so out-of-order mesh-relayed updates don't clobber a newer one; the family endpoint
  returns each contact's latest status.
- **Resources + Smart Matching** (`app/routers/resources.py`): haversine-distance-based
  recommendation with the reasoning returned alongside the pick (Part 12 explicitly asks for
  "show the reasoning," not just a black-box recommendation). ETA is straight-line-distance
  based and flagged `is_simulated_eta: true` — not real routing.
- **Shelters / Hospitals** (`app/routers/places.py`): seeded on first startup with a small
  set of real Karachi-area facilities so the app has something to query immediately — see
  the honesty note in `_seed_demo_reference_data()` in `app/main.py` about these being
  illustrative reference data, not a verified GIS feed.
- **AI abstraction layer** (`app/ai_provider.py`, `app/routers/ai.py`): `AIProvider`
  interface with a deterministic `MockProvider` (keyword-based, handles English/Urdu
  code-switching — this is what correctly parsed the Part 6 example) as the safe default,
  and a real `AnthropicProvider` that activates automatically the moment
  `RESCUENET_ANTHROPIC_API_KEY` is set, with no other code changes needed. Also implements
  `/api/ai/cluster` — naive-but-honest proximity clustering, explicitly flagged as an O(n²)
  approach that's fine for a hackathon dataset and not fine at city scale.
- **Alerts** (`app/routers/alerts.py`): role-gated creation (confirmed 403 for citizens),
  `is_demo` flag required and defaulted `True` — there is no code path in this prototype that
  can mark an alert as an official government warning.
- **Sync batch** (`app/routers/sync.py`): the server-side receiving end of the Android app's
  `SyncWorker` (see the `TODO(Phase 5)` markers it referenced, now filled in on the client —
  see the Android project's updated `SyncWorker.kt`). Dedups exactly like direct incident
  creation.
- **Dashboard statistics** (`app/routers/dashboard.py`): counts, average AI confidence,
  relayed-message count.
- **WebSocket** (`app/websocket.py`, `/ws/incidents`): live push on incident create/update,
  resource assignment, and alert creation — confirmed working with a real connected client
  during development.

## What's intentionally NOT in this phase

- PostGIS-backed spatial queries (Part 12 names it as the target; this prototype uses
  application-level haversine distance instead — correct, just not indexed/scalable)
- Real routing/traffic data for Safe Route ETAs (flagged `is_simulated_eta`)
- A real facility/GIS data feed for shelters/hospitals (currently a small seeded set)
- Push notifications, SMS gateways, or any channel besides the WebSocket + the Android app's
  own local notifications
- Command Center web frontend itself (Phase 7) — this is the API it will call
- Rate limiting / API abuse protection — needed before any public deployment

## Endpoint list

See `/docs` (Swagger UI) for the full interactive reference generated from `app/schemas.py`.
Summary:

```
POST   /api/auth/device-register       Anonymous citizen auth
POST   /api/auth/org-login             Volunteer/Operator/Admin auth

POST   /api/incidents                  Create incident (deduped by event_uuid)
GET    /api/incidents                  List/filter incidents
GET    /api/incidents/{id}             Incident detail
POST   /api/incidents/{id}/updates     Add status update (role-gated)

POST   /api/safety-status              Post "I'm Safe" / status update
GET    /api/family/{user_id}           Family safety board

GET    /api/resources                  List resources
POST   /api/resources/{id}/assign      Assign resource to incident (role-gated)
GET    /api/resources/recommend/{incident_id}   Smart resource matching

GET    /api/shelters
GET    /api/hospitals

POST   /api/ai/analyze-incident               Structure freeform text (Part 6)
POST   /api/ai/analyze-incident/{id}/attach   ...and persist against an incident
POST   /api/ai/cluster                        Proximity-based incident clustering

POST   /api/alerts                     Create alert (role-gated, is_demo required)
GET    /api/alerts                     List active alerts

POST   /api/sync/batch                 Bulk offline-mesh hand-off (Part 21/23)

GET    /api/dashboard/statistics       Analytics aggregates

WebSocket: /ws/incidents               Live incident/resource/alert push
```
